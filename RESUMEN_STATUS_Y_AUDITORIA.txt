RESUMEN DE CAMBIOS: STATUS Y AUDITORIA DE ACCESOS
=================================================

1. CAMPO STATUS EN LA TABLA USERS
----------------------------------

Se agrego un nuevo campo llamado status en la tabla users de la base auth_db.

Tipo de dato:
    SMALLINT

Valores permitidos:
    1 = usuario activo
    0 = usuario bloqueado

Valor inicial:
    Todo usuario nuevo se crea con status = 1.

Regla de intentos fallidos:
    Primer intento fallido: status permanece en 1.
    Segundo intento fallido: status permanece en 1.
    Tercer intento fallido: status cambia a 0 y el usuario queda bloqueado.

Cuando status vale 0, el usuario no puede iniciar sesion y el servicio responde
con el estado HTTP 423 (Locked).

La tabla users conserva unicamente el campo status para controlar el estado del
usuario. El contador de intentos NO se guarda en auth_db.

2. NUEVO MICROSERVICIO DE AUDITORIA
-----------------------------------

Se creo un microservicio independiente llamado login-audit-service.

Ubicacion:
    services/login-audit-service

Puerto:
    5004

Este servicio registra todos los intentos de inicio de sesion, tanto correctos
como incorrectos.

3. NUEVA BASE DE DATOS
----------------------

Nombre de la base:
    login_audit_db

Esta base es independiente de auth_db. Se ejecuta dentro del mismo servidor
PostgreSQL, pero utiliza una base de datos separada.

El historial completo de accesos se guarda en la tabla:
    login_attempts

Columnas de login_attempts:
    id               Identificador del registro.
    user_id          Identificador del usuario, si existe.
    username         Nombre del usuario que intento acceder.
    registered_at    Fecha y hora del intento.
    successful       Indica si el acceso fue exitoso.
    attempt_number   Numero del intento fallido consecutivo.

4. COMO FUNCIONA EL LOGIN
-------------------------

1. El usuario envia su nombre y contrasena al auth-service.
2. auth-service valida los datos contra auth_db.
3. auth-service envia el resultado al login-audit-service.
4. login-audit-service guarda el registro en login_audit_db.login_attempts.
5. El microservicio de auditoria cuenta los fallos consecutivos del usuario.
6. Al tercer fallo, auth-service cambia users.status a 0.
7. Los siguientes accesos son rechazados porque el usuario esta bloqueado.

Los accesos exitosos tambien se guardan en la tabla de auditoria.

6. CONSULTAR EL HISTORIAL
-------------------------

El historial puede consultarse mediante el endpoint:

    http://localhost:5004/api/login-attempts

Tambien puede revisarse desde pgAdmin:

    Base de datos: login_audit_db
    Schema: public
    Tabla: login_attempts

7. SERVICIOS Y PUERTOS
----------------------

auth-service:
    http://localhost:5001

login-audit-service:
    http://localhost:5004

Frontend:
    http://localhost:5173

8. PANTALLA INTERACTIVA
-----------------------

En el frontend se agrego la opcion "Accesos" en la barra de navegacion.

Ruta:
    http://localhost:5173/access-log

Esta pantalla muestra:
    - Usuario.
    - Fecha y hora.
    - Resultado del intento.
    - Numero de intento.
    - Estado de usuario bloqueado.

El boton "Actualizar" consulta nuevamente los registros del microservicio.

9. RESULTADO FINAL
------------------

auth_db.users guarda los datos del usuario y su status 1 o 0.

login_audit_db.login_attempts guarda todo el historial de accesos, fechas,
resultados y numeros de intento.

La informacion de autenticacion y la auditoria estan separadas en dos bases
de datos independientes.
